=== projekt-start | Planung und Datenschicht | 30
Du baust jetzt eine komplette kleine App: eine Aufgabenliste. Das klingt bescheiden, enthält aber alles, was auch grosse Apps ausmacht – Datenmodell, Service, mehrere Komponenten, Benutzereingaben, berechnete Werte und Speicherung.

## Was die App können soll

- Aufgaben mit einem Titel anlegen
- Aufgaben als erledigt markieren (und wieder zurück)
- Aufgaben löschen
- anzeigen, wie viele Aufgaben noch offen sind
- nach «alle», «offen» und «erledigt» filtern
- die Aufgaben behalten, auch wenn man die Seite neu lädt

## Erst planen, dann programmieren

Bevor du eine Zeile schreibst, beantworte drei Fragen. Das machen auch erfahrene Entwickler so.

**1. Welche Daten gibt es?** Eine Aufgabe hat eine Kennung, einen Titel und einen Zustand:

```ts
export interface Aufgabe {
  id: number;
  titel: string;
  erledigt: boolean;
}

export type Filter = 'alle' | 'offen' | 'erledigt';
```

**2. Wo leben die Daten?** In einem Service. Er besitzt die Liste und bietet Methoden an, um sie zu ändern. Komponenten zeigen nur an.

**3. Welche Komponenten braucht es?**

| Komponente | Aufgabe |
| --- | --- |
| `App` | Eingabefeld, Filter, Liste, Zähler |
| `AufgabeZeile` | eine einzelne Aufgabe mit Haken und Löschen-Knopf |

## Das Projekt anlegen

Erstelle ein frisches Projekt (in einem Terminal ausserhalb von `erste-app`):


Wieder mit **CSS** und **ohne** SSR. Öffne den Ordner in VS Code und erzeuge die Bausteine:


## Der Service

Der Service ist das Herz der App. Hier kannst du alles anwenden, was du über Signals, Kapselung und «Kopieren statt Verändern» weisst.

Das Schöne: Ein Service enthält kein HTML. Deshalb kann die folgende Übung deinen Code **wirklich ausführen** und sein Verhalten prüfen, nicht nur seinen Aufbau.

--- code projekt-service | Der AufgabenSpeicher
Schreibe den Service `AufgabenSpeicher` in `aufgaben-speicher.ts`. Das Datenmodell in `aufgabe.ts` ist fertig.

- `liste` – ein **privates** Signal mit einem Array von `Aufgabe`, zu Beginn leer
- `aufgaben` – die öffentliche, nur lesbare Sicht darauf (`asReadonly()`)
- `anzahlOffen` – ein `computed`: Anzahl der nicht erledigten Aufgaben
- `hinzufuegen(titel)` – entfernt Leerzeichen am Rand. Ist der Titel dann leer, passiert nichts. Sonst wird eine neue Aufgabe mit `erledigt: false` angehängt. Jede Aufgabe bekommt eine **eindeutige** `id`: 1, 2, 3 … (auch nach dem Löschen wird keine `id` doppelt vergeben).
- `umschalten(id)` – kehrt `erledigt` bei der Aufgabe mit dieser `id` um
- `entfernen(id)` – entfernt die Aufgabe mit dieser `id`

Ändere das Signal immer mit `update` und einem **neuen** Array.

@solution aufgaben-speicher.ts
import { Service, computed, signal } from '@angular/core';
import { Aufgabe } from './aufgabe';

@Service()
export class AufgabenSpeicher {
  // Signal, aufgaben, anzahlOffen
  private readonly liste = signal<Aufgabe[]>([]);
  private naechsteId = 1;

  readonly aufgaben = this.liste.asReadonly();
  readonly anzahlOffen = computed(() => this.liste().filter((a) => !a.erledigt).length);

  // hinzufuegen, umschalten, entfernen
  hinzufuegen(titel: string): void {
    const sauber = titel.trim();
    if (sauber === '') {
      return;
    }
    const neu: Aufgabe = { id: this.naechsteId, titel: sauber, erledigt: false };
    this.naechsteId++;
    this.liste.update((alt) => [...alt, neu]);
  }

  umschalten(id: number): void {
    this.liste.update((alt) => alt.map((a) => (a.id === id ? { ...a, erledigt: !a.erledigt } : a)));
  }

  entfernen(id: number): void {
    this.liste.update((alt) => alt.filter((a) => a.id !== id));
  }
}

## Die Zeile: Daten rein, Ereignisse raus

`AufgabeZeile` ist eine reine Anzeige-Komponente. Sie kennt den Service nicht. Sie bekommt eine Aufgabe als Input und meldet über Outputs, was der Benutzer will:

| | Name | Typ |
| --- | --- | --- |
| Input | `aufgabe` | `Aufgabe` (Pflicht) |
| Output | `umschalten` | ohne Wert |
| Output | `loeschen` | ohne Wert |

Für den Haken verwendest du eine Checkbox. Ihr Zustand wird mit `[checked]` gebunden, und auf Änderungen reagierst du mit `(change)`:

```html
<input type="checkbox" [checked]="aufgabe().erledigt" (change)="umschalten.emit()" />
```

Die Checkbox ändert die Aufgabe **nicht selbst**. Sie meldet nur den Wunsch. Erst wenn der Service das Signal ändert, kommt über den Input eine neue Aufgabe an, und `[checked]` zeigt den neuen Zustand. So bleibt der Service die einzige Quelle der Wahrheit.

## Die App: alles verbinden

`App` holt den Service mit `inject`, zeigt mit `@for` für jede Aufgabe eine Zeile an und leitet die Ereignisse an den Service weiter:

```html
@for (aufgabe of speicher.aufgaben(); track aufgabe.id) {
  <app-aufgabe-zeile
    [aufgabe]="aufgabe"
    (umschalten)="speicher.umschalten(aufgabe.id)"
    (loeschen)="speicher.entfernen(aufgabe.id)"
  />
}
```

Hier siehst du den ganzen Kreislauf: Service → Signal → `@for` → Input → Anzeige → Klick → Output → Service.

## Der Filter

Der Filter ist ein Zustand der **Anzeige**, nicht der Daten. Deshalb lebt er in der Komponente `App`, nicht im Service:

```ts nocheck
readonly filter = signal<Filter>('alle');
```

Der Typ `Filter` ist die Union `'alle' | 'offen' | 'erledigt'`. TypeScript verhindert damit, dass irgendwo ein Tippfehler wie `'ofen'` gesetzt wird.

Die sichtbaren Aufgaben sind ein klassischer Fall für `computed`: Sie ergeben sich aus zwei Quellen – der Liste im Service und dem gewählten Filter. Ändert sich eine davon, wird neu berechnet.

```ts nocheck
readonly sichtbare = computed(() => {
  const alle = this.speicher.aufgaben();
  switch (this.filter()) {
    case 'offen':
      return alle.filter((a) => !a.erledigt);
    case 'erledigt':
      return alle.filter((a) => a.erledigt);
    case 'alle':
      return alle;
  }
});
```

Mit `switch` über eine Union prüft TypeScript, dass du keinen Fall vergessen hast – wie in der Lektion über Narrowing.

=== projekt-speichern | Aufgaben dauerhaft speichern | 25
Im Moment vergisst die App alles, sobald die Seite neu geladen wird. Die Aufgaben leben nur im Arbeitsspeicher. Jetzt speicherst du sie im Browser.

## localStorage

Jeder Browser bietet einen kleinen Speicher pro Webseite: `localStorage`. Er behält Daten auch nach dem Schliessen des Browsers. Speichern kann er nur **Texte**, jeweils unter einem Namen:

```ts nocheck
localStorage.setItem('name', 'Mia');     // speichern
const name = localStorage.getItem('name'); // lesen: 'Mia' – oder null, wenn nichts da ist
localStorage.removeItem('name');          // löschen
```

## Objekte in Text verwandeln: JSON

Ein Array von Aufgaben ist kein Text. Mit `JSON.stringify` wird daraus einer, mit `JSON.parse` wieder ein Array:

```ts
const aufgaben = [{ id: 1, titel: 'Mathe', erledigt: false }];

const text = JSON.stringify(aufgaben);
console.log(text); // [{"id":1,"titel":"Mathe","erledigt":false}]

const zurueck = JSON.parse(text) as { id: number; titel: string; erledigt: boolean }[];
console.log(zurueck[0].titel); // Mathe
```

`JSON.parse` liefert den Typ `any` – TypeScript kann nicht wissen, was in dem Text steckt. Mit `as Typ` sagst du: «Behandle das als diesen Typ.» Das ist dieselbe Art von Versprechen wie bei `httpResource<...>`: keine Prüfung, nur eine Zusage von dir.

## Automatisch speichern: effect

Du könntest in jeder Methode des Service von Hand speichern. Sicherer ist: **immer speichern, wenn sich die Liste ändert**. Genau dafür gibt es `effect`.

```ts nocheck
constructor() {
  effect(() => {
    localStorage.setItem('aufgaben', JSON.stringify(this.liste()));
  });
}
```

Ein `effect` ist eine Funktion, die Angular einmal zu Beginn ausführt und danach **jedes Mal wieder, wenn sich ein darin gelesenes Signal ändert**. Hier wird `this.liste()` gelesen – also läuft der Effekt bei jeder Änderung der Liste und speichert.

Der Unterschied zu `computed`:

| | `computed` | `effect` |
| --- | --- | --- |
| Zweck | einen **Wert** berechnen | etwas **tun** (speichern, protokollieren) |
| Ergebnis | ein Signal | nichts |
| Einsatz | sehr oft | selten |

> [!WARN] Sparsam mit effect
> Nimm `effect` nur für Dinge, die ausserhalb von Angular passieren: speichern, protokollieren, eine fremde Bibliothek ansteuern. Um aus Signals andere Werte abzuleiten, ist immer `computed` das richtige Werkzeug. Setze in einem `effect` keine anderen Signals.

`effect` wird im `constructor` angelegt. Das ist einer der wenigen Fälle, in denen ein Angular-Service einen Constructor braucht.

## Beim Start laden

Beim Erzeugen des Service liest du den gespeicherten Stand und verwendest ihn als Startwert des Signals:

```ts nocheck
private readonly liste = signal<Aufgabe[]>(this.laden());

private laden(): Aufgabe[] {
  const text = localStorage.getItem('aufgaben');
  if (text === null) {
    return [];
  }
  return JSON.parse(text) as Aufgabe[];
}
```

Beim allerersten Besuch ist noch nichts gespeichert, und `getItem` liefert `null`. Dieser Fall muss abgefangen werden – TypeScript erinnert dich daran, weil `JSON.parse` keinen `null`-Wert annimmt.

Noch eine Kleinigkeit: Die nächste freie `id` darf nach dem Laden nicht wieder bei 1 beginnen, sonst gäbe es doppelte IDs. Sie muss grösser sein als alle vorhandenen.

--- quiz quiz-build
Was ist das Ergebnis von `ng build`?
( ) Ein Programm, das man mit Node.js auf dem Server starten muss. :: Nein – heraus kommen gewöhnliche Dateien für den Browser.
(x) Ein Ordner mit HTML-, JavaScript- und CSS-Dateien, den jeder Webserver ausliefern kann. :: Genau. TypeScript und Angular-Werkzeuge braucht es danach nicht mehr.
( ) Eine einzelne `.ts`-Datei mit dem gesamten Code. :: Der Browser versteht kein TypeScript. Beim Build wird alles in JavaScript übersetzt.

--- quiz quiz-rueckblick
Du willst in deiner App die Anzahl erledigter Aufgaben anzeigen. Wie machst du das am besten?
( ) Ein zusätzliches Signal `anzahlErledigt`, das in `umschalten`, `hinzufuegen` und `entfernen` von Hand angepasst wird. :: Das funktioniert, bis du es an einer Stelle vergisst. Dann zeigt die App eine falsche Zahl.
(x) Ein `computed`, das die erledigten Aufgaben aus der Liste zählt. :: Richtig. Die Zahl folgt aus der Liste – also wird sie abgeleitet, nicht gespeichert. Eine Quelle der Wahrheit.
( ) Ein `effect`, der bei jeder Änderung ein Signal `anzahlErledigt` setzt. :: `effect` ist für Dinge ausserhalb von Angular gedacht. Um Werte aus Signals abzuleiten, nimmt man `computed`.
